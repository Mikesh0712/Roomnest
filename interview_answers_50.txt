[Q1: High-level architecture & data flow]
Answer:
"RoomNest follows a decoupled, three-tier client-server architecture:
1. Client Tier: A Single Page Application built with React 19 and Vite, styled using Tailwind CSS, and hosted globally on Vercel's Edge CDN.
2. Server Tier: A stateless RESTful API built on Node.js and Express, hosted on Render. It handles routing, JWT authentication, role-based authorization, rate limiting, and request sanitization.
3. Database & Media Tier: A cloud-managed MongoDB Atlas cluster with Mongoose ODM for geospatial querying and document storage, combined with Cloudinary for optimized media delivery.

Data Flow: When a user interacts with the UI (e.g. applying a rent filter or selecting a college hub), React state updates trigger an HTTP request via Fetch/Axios to the Express API. The request passes through security middleware (Helmet, CORS, RateLimiter, MongoSanitize), hits the controller/service layer, executes an indexed Mongoose query against MongoDB Atlas, and returns a structured JSON response (`ApiResponse`) back to React to update the Virtual DOM and Leaflet map pins."

---

[Q2: Problem RoomNest solves vs legacy portals]
Answer:
"Legacy portals like MagicBricks and 99acres are designed primarily for families buying or leasing entire apartments. They suffer from three critical flaws for students and young professionals:
1. Lack of Hyperlocal Radius Context: Students need housing within walking or cycling distance (e.g., 300m–1km) of their specific college gate or coaching institute, not just a broad city pin-code.
2. Hidden Operational Costs: Traditional sites list base rent but hide electricity sub-meter surcharges, mess/food charges, maintenance, and rigid lock-in periods. RoomNest provides transparent, all-inclusive cost breakdowns.
3. Student-Specific Filtering: We offer filters for curfew times, meal inclusions (3-time home-style food), gender wings, and verified direct owner listings to eliminate brokerage exploitation."

---

[Q3: Decoupled SPA vs Monolith / SSR]
Answer:
"I chose a decoupled React SPA on Vercel and Express API on Render for three technical reasons:
1. Independent Scaling & Deployment: The frontend consists of static assets served over global CDNs with near-zero latency, while the backend API can scale compute instances independently based on load.
2. Separation of Concerns: The backend serves purely as a headless JSON API, allowing us to easily build a React Native mobile app or third-party partner integrations without modifying the core backend.
3. Developer Velocity: Frontend UI iterations and backend business logic can be developed, tested, and deployed independently without rebuilding a monolithic bundle."

---

[Q4: Environment variable management in dev vs prod]
Answer:
"In local development, environment variables are loaded via `dotenv` from `.env` files (e.g., `PORT`, `MONGO_URI`, `JWT_SECRET`). To prevent credential leakage, `.env` is explicitly included in `.gitignore`, and only sanitized `.env.example` templates are committed to Git.
In production:
- On Render (Backend): Secrets are injected securely via Render's Encrypted Environment Secrets dashboard.
- On Vercel (Frontend): Client-safe variables prefixed with `VITE_` (like `VITE_API_URL`) are injected during the build phase into the client bundle."

[Q5: Handling 100x traffic spike during admission season]
Answer:
"To handle traffic surges, I would implement a multi-layered optimization strategy:
1. CDN Caching: Cache static assets and cacheable GET requests (like static college lists and city hubs) at the Vercel Edge CDN level.
2. Redis In-Memory Caching: Cache frequently read property listings and search results with a 5–10 minute TTL to reduce database query load by up to 80%.
3. Horizontal Autoscaling: Configure Render/Kubernetes horizontal pod autoscaling based on CPU/memory utilization and request throughput.
4. Database Connection Pooling: Configure Mongoose connection pools (`maxPoolSize: 50`) and read-replicas in MongoDB Atlas to distribute read queries across secondary nodes."

[Q6: Frontend graceful degradation on backend failure]
Answer:
"We implement defensive error handling:
1. Error Boundaries & Fallback UI: React Error Boundaries catch rendering crashes and display an informative fallback rather than a blank screen.
2. Cached/Initial State Fallback: The application maintains structured fallback data (e.g., initial verified hub listings) in context state so the user can still browse maps and view UI elements.
3. User Feedback & Retry: Failed API calls trigger non-intrusive Toast notifications (e.g., 'Unable to fetch latest properties. Retrying...') and provide a 'Try Again' button with exponential backoff."

---

[Q7: Request-response lifecycle of Search Listings]
Answer:
"1. UI Event: The user adjusts a filter (e.g., max rent = 7000, type = PG).
2. State Dispatch: React updates local state and fires a GET request to `/api/properties?rent[lte]=7000&type=PG`.
3. Transport: DNS resolves the Render domain, establishing a secure TLS 1.3 HTTPS connection.
4. Express Middleware Pipeline: The request passes through `helmet()` (security headers), `cors()` (origin validation), `apiLimiter` (rate check), and `mongoSanitize()` (injection prevention).
5. Routing & Controller: The request routes to `property.controller.js`, which parses query parameters using Zod validation.
6. Service & Database: `property.service.js` executes an indexed Mongoose query (`Property.find(...)`).
7. Response: Express serializes the result into `{ success: true, count: N, data: [...] }` with HTTP 200.
8. React Virtual DOM: React receives the JSON, reconciles the component tree, re-renders the listing cards, and updates Leaflet map markers without refreshing the page."

---

[Q8: Scaling to 50 cities architecture changes]
Answer:
"1. Database Sharding: Shard the MongoDB cluster by `city` or `regionKey` to partition data across multiple database shards.
2. Geospatial 2dsphere Indexing: Enforce geospatial indexes on `location.coordinates` for sub-millisecond proximity queries.
3. Message Queue for Async Tasks: Use BullMQ or RabbitMQ to handle asynchronous workloads like sending SMS/email booking confirmations, review moderation, and image processing.
4. Distributed CDN & Media Optimization: Cloudinary auto-formats images to modern WebP/AVIF formats based on client device capabilities."

[Q9: Vite vs Create React App (CRA) / Webpack]
Answer:
"Vite provides massive performance improvements over legacy bundlers:
1. Native ES Modules (ESM) in Development: Vite serves source code over native ESM, meaning the browser parses modules on demand rather than bundling the entire application upfront like Webpack.
2. Instant Hot Module Replacement (HMR): HMR speed remains constant regardless of app size.
3. Production Rollup Bundler: For production, Vite uses Rollup with efficient tree-shaking, code splitting, and asset hashing, resulting in significantly smaller bundle sizes."

---

[Q10: State management — Context API vs Redux/Zustand]
Answer:
"For RoomNest's architecture, React's native Context API (`AppContext` and `LanguageContext`) was the optimal choice:
- It eliminates external library overhead while providing centralized state for listings, filters, active modals, comparison queues, and language localization.
- Our state transitions (filtering, comparison modal toggles, language switching) are localized and do not require heavy middleware or complex time-travel debugging found in Redux.
- If the app grows to support complex real-time chat between tenants and landlords, migrating to Zustand would be straightforward due to its minimalist boilerplate."

---

[Q11: Controlled vs Uncontrolled Components]
Answer:
"- Controlled Component: Form inputs whose value is controlled directly by React state via `value` and `onChange` handlers (e.g., our budget slider, property search input, and booking modal form). This ensures a single source of truth and allows real-time validation.
- Uncontrolled Component: Form elements where the DOM handles form data internally, accessed using a `useRef()` hook. We use uncontrolled refs primarily for third-party DOM integrations like Leaflet Map container instantiation."

---

[Q12: `useEffect` lifecycle, dependency array & memory leaks]
Answer:
"`useEffect` manages side effects (API calls, event listeners, timer intervals, and map updates):
- Dependency Array: Passing an empty array `[]` runs the effect once on mount. Passing `[filters, activeCity]` re-runs the effect only when those specific values change.
- Cleanup Function: When mounting listeners or initializing Leaflet map instances, the effect returns a cleanup callback (`return () => map.remove()`) to prevent memory leaks and duplicate map container errors upon component unmounting."

---

[Q13: Virtual DOM & React 19 Compiler improvements]
Answer:
"The Virtual DOM is an in-memory lightweight representation of the real DOM. When state changes, React creates a new Virtual DOM tree, performs a 'diffing' algorithm against the previous tree, and batches updates to only modify the changed DOM nodes.
React 19 introduces the React Compiler, which automatically memoizes components, hooks, and calculations under the hood, reducing the need for manual `useMemo` and `useCallback` optimizations and eliminating unnecessary re-renders."

---

[Q14: React Custom Hooks concept & use case]
Answer:
"A Custom Hook is a JavaScript function starting with `use` that encapsulates reusable stateful logic by composing built-in React hooks.
In RoomNest, a custom hook like `useProperties(filters)` encapsulates fetching, error states, and loading indicators, keeping UI components purely declarative and focused on presentation."

---

[Q15: Client-side routing & avoiding 404s on Vercel]
Answer:
"In Single Page Applications, the browser handles routing on the client. When a user directly visits or refreshes a sub-route (e.g., `https://roomnest.vercel.app/properties/123`), the web server looks for a physical file at that path and returns a 404 if unconfigured.
To solve this, we created `client/vercel.json` with rewrite rules:
`{ 'rewrites': [{ 'source': '/(.*)', 'destination': '/index.html' }] }`
This instructs Vercel to route all incoming requests to `index.html`, allowing the client-side router to load and render the correct view."

---

[Q16: Tailwind CSS architecture & Dark/Light mode]
Answer:
"Tailwind uses utility-first classes compiled into minimal CSS at build time via PostCSS.
In RoomNest:
- The design system uses Tailwind's `class` dark mode strategy.
- When toggling dark mode in `AppContext`, a `dark` class is appended to the root `<html>` element.
- Components use declarative prefixes like `bg-white dark:bg-slate-900 text-slate-800 dark:text-slate-100`, providing smooth transitions without maintaining separate CSS stylesheets."

---

[Q17: Prop Drilling vs Context API]
Answer:
"Prop drilling is the process of passing props down through multiple layers of intermediate components that do not actually need the data, creating tightly coupled, fragile code.
Context API solves this by creating a global context provider. Any deeply nested component (e.g., `ListingCard` or `PropertyDetailModal`) can directly access state and dispatch functions via `useApp()` without intermediate components needing to know about them."

[Q18: Optimizing frontend bundle size]
Answer:
"1. Dynamic Imports & Lazy Loading: Use `React.lazy()` and `Suspense` for heavy modals and relocation calculators so they are loaded only when invoked.
2. Icon Tree-Shaking: Import specific named icons from `lucide-react` (e.g. `import { Shield, Wifi } from 'lucide-react'`) rather than importing the full library.
3. Code Splitting: Leverage Vite's Rollup chunking options in `vite.config.js` to split vendor libraries (`leaflet`, `framer-motion`) into separate cached chunks."

[Q21: Haversine Formula for spatial distance]
Answer:
"The Haversine formula determines the great-circle distance between two points on a sphere given their longitudes and latitudes:
`d = 2r * arcsin(sqrt(sin²(Δlat/2) + cos(lat1)*cos(lat2)*sin²(Δlon/2)))`
where `r` is Earth's radius (6,371 km). In MongoDB, this calculation is performed natively at the database level using `$near` and `$geoWithin` operators on 2dsphere indexes."

---

[Q22: Preventing Map re-rendering flickering on filter change]
Answer:
"In React, re-creating the map DOM element causes visual flickering. We prevent this by:
1. Storing the Leaflet map instance in a React `useRef()`.
2. Initializing the map once in `useEffect` with an empty dependency array.
3. Updating only the marker layer (`L.layerGroup`) when listing filters change, rather than re-instantiating the entire Leaflet map container."

[Q23: Preventing Marker Overlapping (Marker Clustering)]

"When multiple accommodations exist in the same building or narrow lane, markers overlap. The industry solution is Leaflet.markercluster:
- Nearby pins within a certain pixel radius are grouped into a single cluster bubble displaying the count (e.g., '5 Listings').
- Clicking the cluster zooms the map smoothly and expands the pins in a spider-leg layout."

[Q25: Node.js Event Loop & Concurrency]
Answer:
"Node.js uses a single-threaded, non-blocking event-driven architecture powered by Google's V8 engine and libuv:
- The single JavaScript execution thread delegates heavy I/O operations (database queries, network requests, file system tasks) to libuv's background thread pool or kernel asynchronous APIs.
- When an operation completes, its callback or Promise resolution is placed in the Event Loop queue (Microtask queue for Promises, Macrotask queue for timers/I/O).
- This allows Node.js to handle tens of thousands of concurrent connections efficiently with low memory overhead."

---

[Q26: Express Middleware & Execution Order]
Answer:
"Middleware functions in Express have access to `req`, `res`, and the `next` function in the request-response cycle. Execution order is top-to-bottom:
1. `helmet()`: Sets security HTTP headers first.
2. `cors()`: Validates origin before processing payload.
3. `express.json({ limit: '10mb' })`: Parses JSON request body.
4. `mongoSanitize()`: Strips malicious MongoDB operator characters.
5. `apiLimiter`: Checks rate limit quotas before hitting routes.
6. Route Handlers (`/api/properties`, `/api/auth`): Business logic.
7. Centralized `errorHandler`: Catches any thrown errors at the very end."

---

[Q27: Centralized Error-Handling Middleware]
Answer:
"Instead of scattering `try/catch` response formatting across every route, RoomNest uses a centralized error-handling middleware:
- A custom `ApiError` class standardizes status codes, error messages, and operational error flags.
- Any unhandled error passed to `next(err)` triggers the error middleware, which logs the stack trace in development and returns a clean, sanitized JSON response `{ success: false, message: ... }` in production, preventing sensitive server stack traces from leaking."

---

[Q28: HTTP Status Codes usage]
Answer:
"- `200 OK`: Successful GET or PUT/PATCH update.
- `201 Created`: Successful creation of a new resource (e.g., user signup, new property listing).
- `400 Bad Request`: Client-side validation failure (e.g., missing required fields, invalid email format).
- `401 Unauthorized`: Missing or invalid JWT token.
- `403 Forbidden`: Authenticated user lacks permission (e.g., tenant trying to access landlord admin routes).
- `404 Not Found`: Resource does not exist.
- `429 Too Many Requests`: Rate limit exceeded.
- `500 Internal Server Error`: Unhandled server-side exception."

---

[Q29: `PUT` vs `PATCH` in REST APIs]
Answer:
"- `PUT`: Replaces the entire resource. The client must supply all fields; missing fields are overwritten or reset to null.
- `PATCH`: Applies a partial update. Only the fields explicitly sent in the request body are modified (e.g., updating just the `rent` or `verificationStatus` of a property), preserving other existing fields."

---

[Q30: API Rate Limiting implementation]
Answer:
"We implement `express-rate-limit` as global middleware (`/api/`) and strict limits on authentication endpoints (`/api/auth/login`):
- It tracks client requests by IP address within a rolling time window (e.g., maximum 100 requests per 15 minutes).
- If exceeded, it terminates the request with HTTP 429 and `Retry-After` headers.
- This protects the API from Denial of Service (DoS) attacks, brute-force password cracking, and scraping bots."

---

[Q31: Async/Await vs Promises & Error Handling]
Answer:
"`async/await` is syntactic sugar built on top of JavaScript Promises, making asynchronous code look and behave like synchronous code:
- It eliminates 'Callback Hell' and nested `.then().catch()` chains.
- In Express controllers, we pair `async/await` with `try/catch` or an async wrapper utility, passing errors to `next(error)` for centralized handling."

---

[Q32: `helmet` and `express-mongo-sanitize` roles]
Answer:
"- `helmet()`: Secures Express apps by setting crucial HTTP response headers, including `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN` (prevents clickjacking), and `Strict-Transport-Security` (enforces HTTPS).
- `express-mongo-sanitize()`: Inspects incoming `req.body`, `req.query`, and `req.params`, stripping any keys containing `$` or `.` to neutralize NoSQL injection attempts."

---

[Q33: Multer + Cloudinary workflow vs Local Storage]
Answer:
"Cloud platforms like Render have ephemeral filesystems—any file stored locally is lost whenever the server restarts or scales.
Workflow:
1. Multer receives the multipart/form-data image stream in memory buffer.
2. The image stream is uploaded directly to Cloudinary via its SDK.
3. Cloudinary returns a secure CDN URL and public asset ID.
4. The database stores only the string CDN URL in the Property document, keeping database size small and image delivery fast."

[Q34: `process.env` security & Secret leakage prevention]

"`process.env` is Node's global object providing access to runtime environment variables:
- Secrets are never hardcoded in source code or committed to Git (`.gitignore` enforces this).
- In production, secrets are injected directly into the execution environment by the cloud host (Render).

SECTION 5: DATABASE — MONGODB, MONGOOSE & DATA MODELING (Q35 - Q41)

[Q35: MongoDB (NoSQL) vs Relational (PostgreSQL/MySQL)]
Answer:
"MongoDB was chosen because rental listings possess flexible, semi-structured schemas:
1. Dynamic Property Attributes: Different property types (1BHK Flat vs Boys PG vs Shared Hostel) have varying sub-document structures (curfew times, meal plans, amenities array, house rules).
2. Native JSON/BSON Storage: Frontend React components consume JSON natively, eliminating complex Object-Relational Mapping (ORM) overhead.
3. Native Geospatial Queries: MongoDB has built-in 2dsphere indexing and operators like `$near` and `$geoWithin` optimized for spatial discovery."

---

[Q36: Mongoose Schema Design overview]
Answer:
"RoomNest utilizes modular Mongoose schemas:
- `User`: Handles authentication (name, email, passwordHash, role: tenant/owner/admin, phone, verifiedStatus).
- `Property`: Contains title, rent, deposit, maintenance, locality, coordinates (`{ type: 'Point', coordinates: [lng, lat] }`), amenities array, houseRules sub-document, and `owner` (ref: 'User').
- `VisitBooking`: Tracks scheduled in-person property visits linking `tenantId`, `propertyId`, preferred date/time slot, and status (pending/confirmed/cancelled).
- `Review`: Tracks tenant ratings, verified stay badges, and comments."

---

[Q37: MongoDB 2dsphere Indexing]
Answer:
"A `2dsphere` index supports queries that calculate geometries on an earth-like sphere.
In Mongoose:
`propertySchema.index({ 'location.coordinates': '2dsphere' });`
This enables sub-millisecond execution of queries like finding all PG accommodations within a 1,000-meter radius of a university without performing slow table scans."

---

[Q38: Embedding vs Referencing in Mongoose]
Answer:
"- Embedding (Denormalization): Storing data directly inside a document (e.g., `amenities: ['WiFi', 'AC']` or `houseRules: { curfew: '9:30 PM' }`). Best when data is always retrieved together and has a 1:1 or small 1:Few relationship.
- Referencing (Normalization): Storing an `ObjectId` reference to another collection and using `.populate()` (e.g., `owner: { type: Schema.Types.ObjectId, ref: 'User' }`). Best when data is shared, updated independently, or has a 1:Many/Many:Many relationship to prevent document unbounded growth (16MB BSON limit)."

---

[Q39: NoSQL Injection Prevention]
Answer:
"NoSQL injection occurs when attackers submit query objects like `{ 'username': 'admin', 'password': { '$ne': '' } }`, which MongoDB interprets as 'password not equal to empty', bypassing authentication.
Prevention:
1. We sanitize all input using `express-mongo-sanitize`.
2. We enforce strict schema and type validation using Zod and Mongoose schemas before queries execute."

---

[Q40: Mongoose Hooks (`pre('save')`) for Password Hashing]
Answer:
"We use Mongoose middleware hooks to decouple security logic from controllers:
```javascript
userSchema.pre('save', async function(next) {
  if (!this.isModified('password')) return next();
  this.password = await bcrypt.hash(this.password, 12);
  next();
});
```
This guarantees that whenever a user is created or updates their password, it is automatically salted and hashed before reaching the database."

---

[Q41: ACID Transactions in MongoDB]
Answer:
"MongoDB supports multi-document ACID transactions via sessions (`client.startSession()`):
- When a student confirms a booking and pays a token deposit, a transaction ensures both the `VisitBooking` status update and the `Property` availability status change commit together.
- If any operation fails, `session.abortTransaction()` rolls back all writes, ensuring zero data inconsistency."

SECTION 6: AUTHENTICATION, SECURITY & NETWORKING (Q42 - Q47)
================================================================================

[Q42: JWT Authentication Workflow]
Answer:
"1. Login: User sends email and password to `/api/auth/login`.
2. Verification: Server verifies user existence and compares password hash via `bcrypt.compare()`.
3. Token Signing: Server signs a JWT payload containing `{ id: user._id, role: user.role }` using `JWT_SECRET` and expiration (`7d`).
4. Transmission: Token is returned to client and stored in memory or secure HTTP-only cookies.
5. Authenticated Requests: Client attaches `Authorization: Bearer <token>` header to protected requests.
6. Middleware Verification: Express middleware uses `jwt.verify(token, JWT_SECRET)` to validate signature and attaches the decoded user object to `req.user`."

---

[Q43: JWT Structure & `JWT_SECRET` role]
Answer:
"A JWT consists of 3 base64url-encoded parts separated by dots: `Header.Payload.Signature`.
1. Header: Specifies algorithm (e.g. HS256) and token type.
2. Payload: Claims/data (e.g. userId, role, expiration).
3. Signature: `HMACSHA256(base64UrlEncode(header) + '.' + base64UrlEncode(payload), JWT_SECRET)`.
`JWT_SECRET` is the server's private mathematical key. If an attacker tampers with the payload (e.g., changing their role from 'tenant' to 'admin'), the server's signature check fails immediately."

---

[Q44: Why sensitive data is forbidden in JWT payload]
Answer:
"JWT payloads are only Base64-encoded, **not encrypted**. Anyone who intercepts or inspects the token can paste it into `jwt.io` and read every claim in plaintext.
Therefore, passwords, credit card numbers, or sensitive PII must never be placed in a JWT payload—only non-sensitive identifiers like `userId` and `role`."

---

[Q45: Bcrypt Hashing vs Encryption & Salt concept]
Answer:
"- Hashing vs Encryption: Encryption is two-way (data can be decrypted with a key). Hashing is a one-way mathematical function designed to be irreversible.
- Salt: A cryptographically random string generated and prepended to the plaintext password before hashing.
- Why Salt is Essential: It ensures that identical passwords produce completely different hash values, defeating pre-computed Rainbow Table attacks."

---

[Q46: CORS & Whitelist rationale vs `*`]
Answer:
"CORS (Cross-Origin Resource Sharing) is a browser security mechanism that restricts a webpage from making AJAX requests to a different domain.
- Leaving CORS as `*` allows any malicious website to make cross-origin requests on behalf of users.
- In RoomNest, we configure explicit origin whitelisting in `server/src/app.js`, restricting allowed origins strictly to `https://roomnest.vercel.app` and local development ports (`http://localhost:5173`)."

---

[Q47: Role-Based Access Control (RBAC)]
Answer:
"RBAC restricts API endpoints based on user permissions:
- We implement a reusable middleware factory: `authorize('landlord', 'admin')`.
- After `authMiddleware` verifies the JWT and attaches `req.user`, the authorization middleware verifies if `req.user.role` matches the required roles.
- If a tenant tries to delete a property listing, the middleware rejects the request with HTTP 403 Forbidden before it ever reaches the controller."

[Q48: MongoDB Atlas `0.0.0.0/0` Whitelist Explanation]
Answer:
"Why `0.0.0.0/0` is necessary:
Cloud hosting platforms like Render and Vercel use dynamic container IP pools that rotate with every deployment and autoscaling event, making static IP whitelisting impossible without costly dedicated static IP add-ons.

Why it is completely secure:
Network whitelisting is merely the outermost perimeter. The database is protected by:
1. SCRAM-SHA-256 Authentication with strong, unique database credentials.
2. TLS/SSL encrypted connection strings in transit.
3. Database credentials stored exclusively in encrypted environment variables inaccessible to the public.
4. HTTP layer access restricted to the verified frontend domain via CORS."

---

[Q49: Cold Start Phenomenon & Mitigation]
Answer:
"- Cause: On free-tier cloud containers (like Render Free), idle containers spin down to save compute resources after 15 minutes of zero traffic. The next incoming request triggers a container boot, taking 30–45 seconds.
- Mitigation:
  1. For production/demos: Configure a free automated HTTP monitoring tool (like UptimeRobot) to send a lightweight GET request to `/api/health` every 5 minutes, keeping the container warm 24/7.
  2. For enterprise scale: Upgrade to always-on instances with min-replicas = 1."

---

[Q50: Step-by-Step Live Debugging Process (403 / CORS Error)]
Answer:
"If a live demo encounters an error, I follow a disciplined 4-step triage process:
1. Browser DevTools Inspection:
   - Check the **Network Tab**: Inspect the failed request's Status Code, Request Headers (`Origin`, `Authorization`), and Response Headers (`Access-Control-Allow-Origin`).
   - Check the **Console Tab**: Check if the browser blocked the request due to CORS preflight failure or Content Security Policy (CSP).
2. Backend Cloud Logs:
   - Open Render live log streaming to verify if the server received the request, if it was rejected by middleware, or if a database query failed.
3. Environment Variable Verification:
   - Check if `CLIENT_URL` on Render matches the exact deployed Vercel domain (e.g., verifying `https://` protocol and no trailing slash mismatches).
4. Direct Endpoint Isolation:
   - Send an isolated `curl` or Postman request directly to `https://roomnest-m8uu.onrender.com/api/health` to confirm database connectivity independently of the frontend."
